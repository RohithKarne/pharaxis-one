# MIMS case form product review — 17 November 2026

**Recommendation:** Replace the three numbered steps on an existing case with **Case Details** and **Activity**. Keep a compact case header with status, owner, priority, date received and one primary action for the case type. Keep New Case as a short intake form. Put optional and specialist fields behind relevant sections, with one clear case save.

Reviewed the working checkout based on `462c0744`, branch `feat/mims-reports-caseform-governance-remediation`, including uncommitted case-form changes. Three sub-agents reviewed the three steps in separate source copies. This is a product and source-code review. Findings describe the checked-in and working-tree logic, not legal advice or a live acceptance sign-off. No application files were changed.

The [field inventory](MIMS_CASE_FORM_FIELD_INVENTORY_2026-11-17.md) lists 305 configured field entries across 29 field-configuration sections. It shows both organisations' effective flags, the storage source used by the app's usage counter and the local aggregate counts. Hard-coded fields, action screens and conditional behavior are covered below.

## Proposed agent workflow

```text
New Case → record what is known
               ↓
Case Details → Primary Reporter · case-type details · optional sections
     │         Save Case → validates and saves pending edits across sections
     │
     ├─────── Activity → correspondence · internal notes · files · case links · history
     │
     └─────── Next action → MI: Build Response
                             AE: Hand Off to Safety
                             PC: Route to Quality
```

**Case Details** should open with fields that support the agent's immediate task. An existing case should open directly to the requested section when followed from a link. The expanded Primary Reporter card, case-type data separation, and hand-off checklists are useful patterns to retain. Destructive and admin-only actions belong behind a clearly named action menu. Activity should distinguish internal comments from external correspondence.

## What “required” means

| Moment | Existing application behavior | Recommendation |
|---|---|---|
| **Create case** | Manual New Case requires organisation, case type, and both reporter names in the UI. The API schema requires case type and allows an omitted reporter object. When supplied, the create route checks controlled values such as reporter country and type. AE and PC intake can collect additional details. | Keep organisation and case type clear. Define and approve an explicit **incomplete intake** path for unavailable information, especially for AE/PC. Align create UI and API. Do not infer that missing information should prevent capture from the requirements for transmission. |
| **Save a section** | The organisation's field configuration can require fields. Hidden or disabled fields are generally excluded by the server engine, but some conditional rendering rules are separate from that engine. The contact path additionally refuses an explicitly blank first name on edit. | Show one required indicator with the reason for the rule. Use the same applicability condition and field name in UI and server. Keep invalid edits visible with an exact message and the field link. |
| **Send an MI response** | The current send check looks for a named contact, an inquiry question summary, a Yes/No AE/PC screen, and a linked or converted AE/PC case when Yes. Product is a warning. Off-label and solicited clearance, and prescribing information, can add checks. Approve/Send use signature and permission controls and the selected channel has its own delivery needs. | Keep checks and signatures at the response action. Resolve the actual requester/recipient consistently. Explain blockers next to the action and link to the missing fields. |
| **Hand off an AE** | Case validity checks reporter, patient, suspected product and event. The transmission route has a mismatch between the assessor output and the property it reads. | Keep four separate checklist items and correct the gate before redesign. Verify both a complete and incomplete synthetic AE. Do not make the form imply that all four are prerequisites for creating a case. |
| **Route PC to Quality** | The current checklist requires a complainant with name/email/phone, a product and complaint description. Injury triggers a linked AE requirement. Lot is a warning. Counterfeit and field-alert signals are handled separately. | Keep the Quality checklist. Put injury and harm near one another while distinguishing actual injury from potential harm. Preserve severity, clock and hand-off logic pending an agreed source of truth. |

**Snapshot of stored Required flags.** Both organisations have the same 13 non-hidden, non-disabled Required rows: five shared case fields (Case Number, Date Received, Case Type, Case Status and Organisation), two contact-name fields, two MI fields (MI Category and Question Summary), one AE field (AE Status), and three PC fields (PC Status, PC Category and Complaint Description). This list includes system-filled values and is separate from action-specific gates.

**Simplify first:** remove the duplicate wizard navigation and duplicate Save buttons, replace misleading completion ticks, move Response/hand-off CTAs out of general workflow, and hide optional detail behind its relevant task. Keep the existing case data and its audit history. Defer merging reporter, patient, narrative and drug storage until each downstream consumer agrees on the source.

## Product approval sequence and acceptance

1. **Triage and verify F1–F11.** Prioritise the save-state, privacy and AE hand-off risks; agree separate dispositions for risk/gate logic and display simplification.
2. **Approve the Case Details + Activity wireframe.** Keep one entry point for the case-type action and one normal Save Case. If operational observation shows a guided intake is still needed, limit it to New Case.
3. **Approve the field disposition by organisation.** Use compact defaults and conditional fields, with legacy data available to authorised users. Confirm downstream use and historical values for every proposed removal from capture.
4. **Walk synthetic MI, AE and PC cases.** Verify manual/Inbox/Portal capture where applicable; incomplete intake; pending edits surviving navigation and reload; configured visible and conditionally hidden required fields; role and historic-version locks; MI Send, AE hand-off and PC Route to Quality with positive and negative examples; and no identity recovery through erased reporter fallbacks. Demonstrate the receiving output where data crosses a system boundary.

## Scope and verification limits

- The audit covers manual New Case, the saved case workspace and action screens it opens, and differences found in email/portal intake where they affect the same fields. Template administration, reporting UI, integration setup and CP Portal itself were followed only where a case-form field depends on them.
- The term **hide** means hide from new capture or move behind an optional section. Preserve recorded values, historical versions and audit history. No field should be physically deleted on this review alone.
- Use sources under `apps/mims/frontend/src/modules/cases/` for the frontend filenames and under `apps/mims/backend/{routes,services}/` for validation and persistence. Organisation field configuration can change the fields shown and the mandatory flags.
- Verified in this review: current source paths and local read-only aggregate configuration/usage for Calder and Vanaja. The browser screenshots supplied in this conversation informed the design critique. Live UI permissions, conditional render states, save and reopen, outbound payloads, and receiving screens were not exercised. No actual case was changed or transmitted.
- Verify store, persistence, permission, historical visibility and receiving output before merging any duplicate. Test tab switches, an existing record, read-only roles, and each relevant positive and negative gate with synthetic cases.
